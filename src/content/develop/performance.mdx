# Performance

Myriad is built so a module costs nothing until it does something, and the **Profiler** window (or `.profiler on`)
shows what each module, service and listener costs, in milliseconds per second. To keep an addon cheap:

- **Work per tick, draw per frame.** A render handler runs a few hundred times a second; the world changes twenty. Put
  what you find (targets, colours, paths) in a `TickCached` and read it from the render handler.

  ```java
  private final TickCached<List<Entity>> targets = TickCached.of(() -> targetSettings.query().range(range.get()).list());

  @Subscribe(inGame = true)
  private void onRender(Render3DEvent e) {
      for (Entity t : targets.get()) draw(e, t);   // worked out once per tick, however many frames read it
  }
  ```

- **Per chunk, not per tick.** Anything about blocks goes in a `ChunkCache` (redone only when a block in the chunk
  changes) with a mesher, so a frame is one draw per chunk. See [Drawing](/docs/develop/rendering#per-chunk).
- **Say what you listen for.** `@Subscribe(inGame = true)`, `packets = {...}` on packet handlers, and no handler at all
  for something you need now and then (`Myriad.events().listen` returns a `Subscription` to drop).
- **Cache what the game recomputes.** `Threats.worst()`, `Inventory.attackCharge()` and friend lookups are cached per
  tick already; `Targets.query().list()` isn't.
- **Hooks**: check `hooked()` before building an expensive input for a hook you declare; keep render-thread handlers
  quick.
- **Spread big work over ticks.** A `TickBudget` says how long a loop may still run this tick ("as much as fits in
  2 ms, nearest first, carry on next tick"); a job's steps get one from `ctx.budget()`. The job runner itself costs
  about 70 ns a tick per running job.
- **Measure.** Anything over a millisecond per second in a tick handler, or a few in a render handler, is worth a look.

## What the Profiler tells you

Each row is an owner (a module, a service, a listener) with its milliseconds per second in tick, render and other
handlers. Running jobs get rows of their own, named "Job Owner › job", whose time is also part of the job runner's.
Where the numbers point at one of the patterns above, the row is marked `*` and the hint is listed under the table
(`.profiler` prints it too):

| Hint | When | Look at |
|---|---|---|
| reads many blocks | a handler reads more than 5,000 blocks a second through the level (250 a tick) | a `ChunkCache` |
| render handlers | more than 2 ms a second in render handlers | a `TickCached` |
| over its budget | a job's tick ran past its 2 ms budget | its steps stopping when `ctx.budget()` runs out |

`.profiler` also shows the blocks a second each owner reads, when it reads any.

## `.bench`

In a dev run (`-Dmyriad.dev`, which the template's and core's run configs set), `.bench` measures core's hot paths on
your machine: posting an event, a hook call with and without a contribution, a block read, a `BlockScan` of your
chunk, a blueprint's positions in reach, solving a wall of placements and a job tick. Each line is the mean time and
the bytes allocated per call, measured warm. The numbers are for comparing a change with what came before on the same
machine, not with someone else's; core's are in the changelog for each release.
